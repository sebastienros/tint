# Fuzz campaign, 2026-10-25

`tools/Tint.Fuzz` (see its [README](../../tools/Tint.Fuzz/README.md)) against TextMateSharp 2.0.4 (Onigwrap) reading
the same grammar files, every bundled grammar, Dark+ on both sides; token and style findings judged by vscode-textmate
9.3.2 over vscode-oniguruma (`tools/Tint.CorpusCheck/referee`, every grammar loaded).

- Machine: Apple M4 Pro (macOS 15.8.1 arm64, 14 cores), .NET 10.0.11.
- Seed 20261025, 20 minutes (20 min 21 s with the last inputs), 12 workers; per-line time limit 10 s on both sides;
  lines over 1 s reported; a line over 60 s is a hang.
- 12,484 inputs, 731,709 lines, 37.6 million characters over the 84 grammars (140 to 560 inputs per grammar: an input
  with a long line holds its worker longer).
- Time spent tokenizing, summed over threads: Tint 585 s, TextMateSharp 12,623 s.

### Fixed in Tint

- A `begin` rule without `end`: vscode-textmate gives it `￿` as its end, which never matches, so the rule stays
  open to the end of the line; Tint used the empty pattern, which matched at once and popped the rule. VS Code's XML
  comment rule has one (`--(?!>)` with no end): on `<!------` Tint marked the second `--` invalid, vscode-textmate
  does not. Fixed, with a regression test (`RuntimeTests.ABeginRuleWithoutEndStaysOpenToTheEndOfTheLine`).

### Differences that stay

- GregsEx work limit (C): after a 7,548-character line of `:::`, one search of the C grammar's function patterns
  reaches GregsEx's work limit and counts as no match (`Tokenizer.LimitExceededCount` goes up by one), so
  `Py_DECREF(data);` is read as a function definition; vscode-oniguruma finds the match and reads a call. The design
  treats an exhausted search as no match on purpose (a bounded engine); the input is kept for GregsEx.
- Registry contents (CoffeeScript): vscode-textmate collects a grammar's
  dependencies from its patterns and includes but not from its captures, so `source.js`, which CoffeeScript embeds
  in a capture only, is not loaded when CoffeeScript is the only grammar asked for, and the backtick block is not
  retokenized. With `source.js` loaded (as in a Tint registry with the bundled grammars, or a VS Code session that
  opened a JavaScript file), vscode-textmate tokenizes exactly as Tint. The referee loads every grammar.

PHP and SQL were slow only on first use (lazy pattern parsing on a busy machine). Long lines are quadratic in every
TextMate tokenizer (each token restarts the searches from its end); VS Code stops tokenizing lines longer than 20,000
characters by default (`editor.maxTokenizationLineLength`). Within that, Tint is as fast as vscode-textmate on
TypeScript, Dart and snippets and much faster than TextMateSharp everywhere, but three to five times slower than
vscode-textmate on TSX, C#, LaTeX, JSON Lines and Batch, and 200 times slower on the YAML line: some patterns cost
GregsEx far more than Oniguruma on long inputs. The inputs are kept for GregsEx; finding the patterns is a follow-up.
